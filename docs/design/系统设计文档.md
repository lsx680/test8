## 1 设计目标与原则

### 1.1 设计目标

本设计以需求规格说明书 §1.5 的建设目标（G1~G6）为验收基准，逐项给出设计层面的响应：

| 目标 | 设计响应 | 验收判据 |
| --- | --- | --- |
| G1 全流程闭环 | 7 个业务模块覆盖「题库—组卷—考试—答题—判分—阅卷—发布—统计—归档」；31 张表承载全链路数据 | 每个环节均有接口（§5.6）与数据表（§4.5），需求追踪矩阵可逐条落到章节 |
| G2 公平可靠 | 服务端权威计时（§3.5.4）、题目脱敏（§3.5.3）、幂等交卷（§3.1.6）、防作弊留痕（§3.5.6） | 异常场景测试用例全部通过（§7） |
| G3 阅卷效率 | 客观题交卷即判分，主观题进入阅卷队列；双评与仲裁状态机（§3.6） | 1000 份答卷 10s 内完成客观判分（NFR-03） |
| G4 教学数据 | 单场统计、题目质量（难度/区分度）、知识点失分分布，物化到 `st_*` 表（§3.7） | 10 万答卷规模统计查询 ≤3s（NFR-04） |
| G5 安全合规 | JWT + RBAC 双层校验（功能权限 + 数据权限）、bcrypt、审计留痕（§3.2、§6.1） | 越权用例 100% 返回 401/403（NFR-07） |
| G6 可追溯交付 | 需求编号 → 用例 → 设计章节 → 接口 operationId → 数据表 → 测试用例 六向可追溯（§1.3、§5.6） | 追踪矩阵覆盖率 100%，无孤立设计项 |

### 1.2 设计原则

1. **需求驱动，不创造需求**：所有模块、接口、数据表均可回溯到 REQ/NFR 编号；未被需求覆盖的能力一律不做，避免毕设范围膨胀。
2. **分层单向依赖**：调用方向固定为 `routes → controllers → services → models → MySQL`，禁止反向与跨层调用；跨模块协作只允许 service 之间通过显式方法调用。
3. **服务端是唯一权威**：考试时间、剩余时长、判分结果、权限判定一律以服务端为准；客户端倒计时、前端菜单隐藏只作体验优化，不构成安全边界（需求 §3.3 第 4 条）。
4. **幂等优先**：交卷、答案暂存、考试发布、备份触发等写操作按"幂等键 + 状态机 + 行锁"实现，重复请求不产生副作用（NFR-13）。
5. **最小暴露**：考试进行中的题目接口在 SQL 查询后就剥离 `correct_answer`、`analysis`、`scoring_points`；日志与响应永不出现密码、令牌全文（NFR-06、NFR-08）。
6. **快照优先于引用**：题目/试卷内容在组卷与开考时固化为 JSON 快照；题库变更不回写历史考试（C-15）。
7. **软删除 + 引用保护**：核心业务数据只标记 `status/deleted_at`；被引用数据禁止物理删除（C-16）。
8. **契约先行，轻量可运维**：先定 OpenAPI 与 DDL，再写代码；单体部署，仅依赖 Node.js + MySQL + Nginx，不引入消息队列、Redis、微服务（C-05）。

| 层次 | 技术 | 版本 | 用途 | 选型依据 |
| --- | --- | --- | --- | --- |

### 2.2 选型对比

**（1）前端框架**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **React 18 + Vite** | 组件化彻底、Hooks 心智简单、Vite 构建快、可按路由分包 | 需自行组合路由与状态方案 | **采用**（C-01 指定） |
| Vue 3 + Vite | 模板语法上手快、官方全家桶完整 | 与需求约定的技术栈不一致 | 备用，不采用 |
| Next.js | SSR/SEO 友好 | 考试系统无需 SEO，SSR 增加部署复杂度 | 不采用 |
| 原生 Canvas/HTML | 零依赖 | 中大型表单与权限路由维护成本过高 | 不采用 |

**（2）后端框架**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **Express 4 + 分层自治** | 极轻量、中间件机制简单、易实现 RBAC 与审计 | 需自行约束分层，无内置 ORM | **采用**（C-02 指定） |
| NestJS | 依赖注入、模块化强 | 学习与构建成本高，对毕设规模属过度设计 | 不采用 |
| Koa 2 | 洋葱模型优雅 | 生态与示例少于 Express | 不采用 |
| Spring Boot | 企业级完善 | 与前端语言栈割裂，部署更重 | 不采用 |

**（3）数据库**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **MySQL 8 单实例单库** | JSON 字段存快照与选项、CHECK/生成列保证约束、运维简单 | 单点风险 | **采用**（C-03、C-08） |
| PostgreSQL | JSONB 与统计函数更强 | 与约束指定的 MySQL 不符 | 不采用 |
| MongoDB | 文档模型贴合题目结构 | 事务与关系型统计（排名、聚合）较弱 | 不采用 |
| SQLite | 零运维 | 并发写入弱，无法支撑 200 并发答题 | 不采用 |

**（4）鉴权方案**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **JWT（HS256）+ RBAC + 令牌版本号** | 无状态、易横向扩展、可实现即时失效 | 需维护刷新令牌白名单表 | **采用**（C-04） |
| Session + Cookie | 服务端可控、易吊销 | 需共享会话存储，单机外扩展困难 | 不采用 |
| OAuth2 / CAS | 支持单点登录 | 需求明确不引入（C-04） | 不采用 |

**（5）异步处理（判分、超时交卷）**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **进程内任务队列 + 定时轮询** | 零中间件、部署简单；配合幂等可重放 | 单机故障时任务需重启后补跑 | **采用**（C-05） |
| Redis + BullMQ | 可靠队列、可视化 | 违反"不引入额外中间件"约束 | 不采用，列为演进方向（§2.3） |
| 数据库轮询（`status=pending` 扫描） | 实现最简、天然幂等 | 轮询间隔带来秒级延迟 | **采用**（作为进程内任务的实现方式） |

### 2.3 不引入额外中间件的论证与演进边界

| 关注点 | 本期方案 | 为什么够用 | 后期演进方向（本期不实现） |
| --- | --- | --- | --- |
| 异步判分 | 交卷时同步完成客观判分（单份 ≤100ms）；失败写入 `grading_status=pending` 由定时任务重放 | 单场 500 人，判分是纯 CPU 计算，无外部 IO | 引入 Redis + BullMQ 做判分队列 |
| 超时自动交卷 | 30s 定时轮询 `status='ongoing' AND deadline_at <= NOW()` | 超时容忍度为分钟级，轮询足够 | 时间轮 / 延迟队列 |
| 缓存 | 进程内 LRU（系统参数、知识点树、权限点），TTL 60s | 数据量小、变更频率低 | Redis 共享缓存 |
| 会话 | JWT 无状态 + 刷新令牌白名单表 | 无状态即可水平扩展 | Redis 存储令牌黑名单 |
| 限流 | 内存令牌桶（登录接口按账号 + IP） | 单机部署，内存计数准确 | Redis 分布式限流 |
| 通知 | 写入 `sys_notification` 表，前端轮询 | 站内通知非实时要求 | WebSocket 推送 |

> **边界声明**：上表右列仅作为论文"总结与展望"的演进讨论，**本期代码不得依赖**。若后续引入，必须保持 `/api/v1` 契约不变。

## 3 系统架构与模块设计

### 3.1 总体架构与技术选型

#### 3.1.1 总体架构

系统采用**单体分层架构 + 前后端分离**形态，物理上分为客户端层、接入层、应用层、数据层四层；逻辑上应用层内部再分 5 个横向层次（见 §3.1.2）。架构图见 `docs/design/架构图.puml`（含分层架构图与部署图两个 `@startuml` 块）。

```
浏览器 SPA（React 18）
      │  HTTPS /api/v1 + JSON
      ▼
Nginx（HTTPS 终止 / 静态资源 / 反向代理）
      │  内网转发
      ▼
Express 应用（Node 18）
  middleware → routes → controllers → services → models
      │  mysql2 连接池（参数化 SQL）
      ▼
MySQL 8（单实例 / 单库 oes / 31 张表）
```

**数据流特征**

1. **同步主链路**：读请求由 controller 装配参数后直接调用 service → model，单次 SQL 或少量 SQL 聚合，避免 N+1。
2. **写事务边界**：所有跨表写入以 service 方法为事务边界（`BEGIN/COMMIT/ROLLBACK`），如「交卷 + 逐题得分 + 阅卷任务 + 成绩变更」在同一事务内完成。
3. **异步旁路**：超时交卷、判分重放、统计物化、备份由进程内定时任务驱动，复用 service 方法（不绕过业务规则）。
4. **学生链路最小化**：考试进行中，学生端只访问 `/attempts/*` 与 `/exams/available`，响应全部经过脱敏投影，不与教师端共享数据组装路径。

#### 3.1.2 逻辑分层与目录约定

后端目录结构（`backend/`）：

```
backend/
├── src/
│   ├── app.js                  # Express 实例装配（中间件顺序在此固定）
│   ├── server.js               # 启动入口（端口、优雅关闭、定时任务注册）
│   ├── config/
│   │   ├── env.js              # 环境变量读取与校验（缺失即启动失败）
```

#### 3.1.5 核心业务流程设计

以下 5 条流程构成系统主链路，详细字段与状态流转见 §3.4~§3.7。

**（1）组卷流程（教师）**

1. 教师选择「手动组卷」：`POST /papers` 提交 `{paperName,totalScore,questions[{questionId,score}]}`。
2. `paperService.createPaper` 校验：试卷至少 1 题、题目去重、题干题目均属于本人/被授权题库、`Σscore == totalScore`；校验失败返回 422 并给出差额与逐题分值明细（REQ-PPM-03）。
3. 同一事务内：写 `pp_paper`、逐条写 `pp_paper_question`（同时固化 `question_snapshot`），并回写 `qb_question.reference_count + 1`。
4. 选择「随机组卷」：`POST /papers/random` 按 `(题型, 难度分布, 知识点范围)` 生成候选池；不足时**不落库**，返回 `shortages[]`（REQ-PPM-02）。
5. 试卷保存后状态为 `draft/published`；一旦被考试引用，`examService` 将其置为 `locked`，此后 `PUT /papers/{id}` 只允许改名称与说明（REQ-PPM-06）。

**（2）开考流程（学生）**

1. 学生进入 `/exams/available`，`examService` 依据 `ex_exam_scope` 展开的 `ex_exam_task` 判定可见性，返回 `canStart` 与 `rejectReason`。
2. 点击开考：`POST /exams/{examId}/attempts`，`attemptService.startAttempt` 在**同一事务**内执行 4 步校验：
   - 任务存在且 `student_id = 当前用户`（数据权限，否则 403）；
   - `NOW() BETWEEN start_time AND end_time`（否则 409 `EXAM_NOT_IN_WINDOW`）；
   - `attempts_used < attempts_allowed`（否则 409 `ATTEMPT_QUOTA_EXCEEDED`）；
   - 不存在 `status='ongoing'` 的答卷（存在则直接返回该答卷，实现断线重连语义）。
3. 校验通过：插入 `ex_exam_attempt`，`started_at = 服务端 NOW()`，`deadline_at = LEAST(started_at + duration, end_time)`，`attempt_seq = attempts_used + 1`，并 `UPDATE ex_exam_task SET status='doing', attempts_used=attempts_used+1`。
4. 复制试卷快照：按 `pp_paper_question` 逐条插入 `ex_attempt_question`，`question_snapshot` 原样复制（含答案），按 `shuffle_questions` 生成 `order_no`（以 `attempt_id + question_id` 为随机种子，保证同一答卷多次请求顺序稳定）。
5. 返回 `AttemptSession`（含 `remainingSeconds` 与 `serverTime`），**不下发任何答案字段**。

**（3）答题流程（学生）**

1. 前端每 30 秒调用 `GET /attempts/{id}/remaining-time` 校准；本地倒计时仅展示（REQ-EXM-06）。
2. 切题/改答案/每 30 秒自动暂存：`PUT /attempts/{id}/answers` 携带 `answers[{questionId,answer,answerVersion}]`。
3. `attemptService.saveAnswers` 校验：答卷归属、`status='ongoing'`、`deadline_at > NOW()`；按 `(attempt_id,question_id)` 执行 `UPDATE ... SET student_answer=?, answer_version=answer_version+1, answer_saved_at=NOW()`，并用 `answer_version` 做乐观锁，冲突返回 409（前端重新拉取）。
4. 暂存**不修改** `deadline_at`，也不触发判分。
5. 断线/刷新：`GET /attempts/{id}` 返回同一 `remainingSeconds` 与已暂存答案，不重复计时（REQ-EXM-08、NFR-11）。

**（4）交卷与判分流程**

1. 学生点击交卷或服务端判定超时：`POST /attempts/{id}/submit`（超时由 `timeoutSubmit.job` 复用同一 service）。
2. `attemptService.submitAttempt` 使用**条件更新**实现幂等：`UPDATE ex_exam_attempt SET status='submitted', submitted_at=NOW(), submit_type=? WHERE id=? AND status='ongoing'`。
   - 影响行数 = 1：本次为首个交卷请求，继续判分；
   - 影响行数 = 0：说明已交卷或不存在，直接读取当前答卷返回**同一结果**（`replayed=true`），不重复判分（NFR-13）。
3. 固化快照：将 `ex_attempt_question` 标记交卷（禁止后续暂存），并更新 `ex_exam_task.status='submitted'`。
4. 触发客观判分 `gradingService.autoGrade(attemptId)`：
   - 按 `question_type` 取判分器：`single`（集合相等）、`multiple`（按 `grading.multiChoiceStrategy` 全对或半分）、`judge`（布尔相等）、`fill`（逐空字符串归一化后相等）、`short`（不自动判分，进入阅卷队列）。
   - `final_score = auto_score`，`is_correct` 记录；主观题 `grade_status='pending'` 并写 `mk_grading_task`。
   - 写 `ex_exam_attempt.objective_score / subjective_score / total_score`，`grading_status = manual_pending | auto_done`。
5. 失败处理：若判分异常，事务回滚并保持 `status='submitted', grading_status='pending'`；`gradingReplay.job` 每 60s 扫描重放。判分逻辑**先清零再重算**，保证可重放且结果一致。

**（5）成绩统计流程**

1. 阅卷完成（`mk_grading_task` 全部 `done`）后，教师 `POST /exams/{id}/publish-scores`；若仍有未完成任务返回 409（REQ-STA-05）。
2. 发布：`ex_exam.score_status='published'`，写 `score_published_at`，向参考学生批量写 `sys_notification`。
3. `statRefresh.job` 在「交卷 / 阅卷完成 / 成绩发布 / 重判」事件后刷新 `st_exam_stat`、`st_question_stat`、`st_knowledge_stat`（物化汇总，避免每次请求全表聚合）。
4. 单场统计：`GET /exams/{id}/statistics` 优先读 `st_exam_stat`（存在且 `calc_at` 在 5 分钟内即直接返回），否则实时聚合后回写。
5. 题目质量：正确率 = 正确人数 / 有效作答人数；难度系数 = 平均得分 / 满分；区分度 = 高分组（前 27%）平均得分率 − 低分组（后 27%）平均得分率（REQ-STA-03）。

#### 3.1.6 考试快照与幂等设计

**（1）三层快照**

| 层级 | 落点 | 生成时机 | 特性 |
| --- | --- | --- | --- |
| 题目版本快照 | `qb_question_version.snapshot` | 题目创建/修改时 | 保证题目历史可追溯（REQ-QBM-02） |
| 试卷题目快照 | `pp_paper_question.question_snapshot` | 组卷保存时 | 锁定试卷后不随题库变化（C-15） |
| 答卷题目快照 | `ex_attempt_question.question_snapshot` | 开考时 | 每份答卷独立固化，含答案与分值，服务端判分依据 |

**关键规则**：判分只读 `ex_attempt_question.question_snapshot`，**绝不回查 `qb_question`**。因此题库修改、标准答案修正（除管理员显式触发重判外）均不影响进行中或历史考试。

**（2）幂等设计矩阵**

| 操作 | 幂等键 | 实现机制 | 重复请求结果 |
| --- | --- | --- | --- |
| 交卷 | `attempt_id + status='ongoing'` | 条件 UPDATE + 影响行数判定 | 返回首次交卷结果，`replayed=true` |
| 答案暂存 | `(attempt_id, question_id)` | 唯一索引 + `answer_version` 乐观锁 | 覆盖写，不产生重复作答行 |
| 开考 | `(exam_id, student_id, active_flag)` | 生成列唯一索引 | 返回已存在的进行中答卷 |
| 发布考试 | `exam_id + status='draft|published'` | 条件 UPDATE | 返回已发布结果，任务不重复生成（`uk_task_exam_student`） |
| 判分 | `attempt_id` | 先清客观分再重算；`mk_grading_task.attempt_question_id` 唯一 | 结果一致，无重复任务 |
| 备份触发 | 内存锁 + `status='running'` 记录 | 存在运行中记录时拒绝 | 返回 409 或当前运行记录 |

**（3）答卷状态机**

```
(无) --开考--> ongoing --交卷(条件更新)--> submitted
submitted --自动判分成功--> grading --判分完成--> graded
submitted --判分失败--> submitted(待重放) --重放--> grading
graded --人工阅卷全部完成--> graded
graded --复核采纳改分--> reviewed
ongoing --超过 deadline+宽限--> expired（由超时任务置为 submitted 后判分，expired 仅用于异常兜底）
```

约束：`ongoing → ongoing` 不允许（唯一索引拦截）；`submitted` 之后任何答案写入均返回 409。

#### 3.1.7 异常与错误码规范

**异常分层**

| 异常类型 | 来源 | HTTP | 处理方式 |
| --- | --- | --- | --- |
| `ValidationError` | zod 校验 | 422 | 返回字段级 `errors[]` |
| `BusinessError(code)` | service 主动抛出 | 400/409 | 返回业务错误码与可读原因 |
| `AuthError` | 认证中间件 | 401 | 统一提示"登录状态失效，请重新登录"，不区分签名错误/过期（防探测） |
| `PermissionError` | 鉴权/数据权限中间件 | 403 | 记录审计，返回"无权访问该资源" |
| `NotFoundError` | model 查询为空 | 404 | 统一"资源不存在或已删除" |
| `DbError` | MySQL 唯一键/外键/死锁 | 409/500 | 唯一键 → 409 并映射业务含义；死锁 → 重试 1 次后 500 |
| `UnknownError` | 兜底 | 500 | 记录 traceId，响应不含堆栈 |

**统一响应契约**（详见 §5.2）：

```json
{ "code": 0, "message": "ok", "data": {} }
```

失败示例：

```json
{
  "code": 40301,
  "message": "无权访问该资源",
  "errors": null,
  "data": null
}
```

**错误码编码规则**：`HTTP 状态码(3位) + 模块序号(2位) + 序号(2位)`，共 7 位；模块序号 01=UAM、02=QBM、03=PPM、04=EXM、05=MRK、06=STA、07=SYS。完整错误码表见 §5.4。

**日志规范**：结构化 JSON，字段固定为 `{timestamp,traceId,userId,roleCode,method,path,status,code,durationMs,msg}`；错误日志额外包含 `errorCode,stack`（仅写日志，不进响应）；密码、令牌、标准答案、考生答案**禁止**入日志。

**（3）状态管理方案**

| 状态 | 载体 | 说明 |
| --- | --- | --- |
| 鉴权态（token、user、permissions） | `AuthContext` + `useReducer` | 登录写入；`/auth/me` 拉取权限点；登出清空 |
| Access Token 存储 | **内存变量**（模块级） | 不落 localStorage，降低 XSS 窃取风险 |
| Refresh Token 存储 | `localStorage` | 满足"刷新后保持登录"；配合 CSP、7 天有效期、单次轮换与重放检测缓解风险 |
| 答题会话 | `ExamSessionContext`（`useReducer`） | `answers` 映射、`dirty` 队列、`remainingSeconds`、`saving` 状态 |
| 服务端列表数据 | 页面级 `useApi` hook + 本地缓存 | 分页/筛选变化时重新请求；不引入额外状态库 |
| 全局提示 | `ToastContext` | 成功/失败/警告统一走 `code → message` 映射 |

**答题页数据流**：

```
开考成功 → 写入 ExamSessionContext（attemptId, questions, deadlineAt）
        → useCountdown 以 deadlineAt + serverTime 偏移渲染倒计时
        → 每次作答 dispatch(SET_ANSWER)，标记 dirty
        → useAutoSave：切题立即提交 + 每 30s 提交 dirty 队列
        → PUT /answers 成功：更新 answerVersion、显示"已保存 HH:mm:ss"
        → 每 30s GET /remaining-time 校准；remainingSeconds<=0 自动交卷
        → 交卷后清空本地会话，跳转成绩页
```

### 3.2.4 权限与安全设计

**（1）认证链路**

```
① POST /auth/login
   ├─ 账号存在性校验（统一提示"用户名或密码错误"，不区分，防账号枚举）
   ├─ status 校验：pending → 403 ACCOUNT_PENDING；disabled → 403 ACCOUNT_DISABLED
   ├─ locked_until > NOW() → 423 ACCOUNT_LOCKED（返回剩余秒数）
   ├─ bcrypt.compare(password, password_hash)
   │    ├─ 失败：failed_attempts+1；达到 5 次 → locked_until=NOW()+15min，写安全审计
   │    └─ 成功：清零 failed_attempts，更新 last_login_at/ip
   ├─ 签发 Access Token（HS256，2h）
   └─ 签发 Refresh Token（随机 32 字节，7d）：库中只存 SHA-256 摘要 + jti

② 每次业务请求
   Authorization: Bearer <accessToken>
   ├─ 验签（HS256，JWT_SECRET）→ 失败 401
   ├─ 校验 exp → 过期 401 TOKEN_EXPIRED（前端触发 refresh 后重放一次）
   ├─ 查询 sys_user（内存 LRU 缓存 60s）
   │    ├─ 不存在 / status != active / deleted_at != NULL → 401
   │    └─ payload.tokenVersion != user.token_version → 401 TOKEN_REVOKED
   ├─ 功能权限：permissionCode ∈ 角色权限集合 → 否则 403
   └─ 数据权限：service 层按 ownerId/studentId 过滤 → 越权 403

③ POST /auth/refresh
   ├─ 计算 SHA-256(refreshToken)，查 sys_refresh_token
   ├─ 不存在 / revoked_at != NULL / expires_at < NOW() → 401
   ├─ 用户状态校验（同 ②）
   ├─ 旧记录 revoked_at=NOW(), revoke_reason='rotated'
   └─ 签发新令牌对（新 jti）

④ POST /auth/logout
   └─ revoked_at=NOW(), revoke_reason='logout'
```

**Access Token 载荷**

```json
{
  "sub": 3,
  "username": "S2024001",
  "roleCode": "student",
  "tokenVersion": 1,
  "jti": "0f5c9e2a-...",
  "iat": 1793664000,
  "exp": 1793671200
}
```

> 载荷**不含**密码、邮箱、权限点全量列表（避免令牌膨胀与信息泄露）；权限点在 `/auth/me` 中按角色查询返回。

**（2）双层权限校验（核心约束 1）**

| 层级 | 判定内容 | 实现位置 | 失败响应 |
| --- | --- | --- | --- |
| 功能权限 | 角色是否拥有该接口的 `permissionCode` | `authorize(permCode)` 中间件，基于 `sys_role_permission` | 403 `PERMISSION_DENIED` |
| 数据权限 | 该用户是否有权访问这一条数据 | `service` 层：SQL 条件强制附加 `owner_id = :userId` 或 `student_id = :userId`（管理员跳过） | 403 `DATA_SCOPE_DENIED` |

数据权限的三条硬规则：

1. **教师**：`qb_question_bank.owner_id`、`pp_paper.owner_id`、`ex_exam.owner_id`、以及由考试派生的答卷/成绩/阅卷任务，均按 `owner_id = 当前用户` 或 `qb_bank_authorization` 授权过滤。
2. **学生**：`ex_exam_attempt.student_id = 当前用户`，且不得通过任何接口访问他人答卷（含 `GET /attempts/{id}`，越权返回 403 而非 404，便于审计）。
3. **管理员**：不受数据范围限制，但**不能代替教师组卷**（权限矩阵第 10 项 △），仅可查看与监管。

**实现要点**：数据权限条件由 service 生成并强制拼入 SQL 的 `WHERE`，不依赖 controller 传入的 `ownerId`；禁止使用"前端传 ownerId 后端信任"的写法。示例（伪代码）：

```js
// paper.service.js
const scope = dataScope.build(req.user);      // { sql: 'owner_id = ?', params: [userId] } | null(管理员)
const rows = await paperModel.list({ keyword, status, page, pageSize, scope });
```

| 公告 | 发布 | 查看 | 查看 | 28 |

权限点共 69 个，初始化映射见 `schema.sql` §7.4/§7.5；新增接口必须同时新增权限点并写入 `sys_role_permission`，否则视为漏配（测试用例覆盖）。

**（4）密码与凭据安全**

| 项 | 规则 |
| --- | --- |
| 哈希算法 | bcrypt，`cost = 10`（不低于 10，NFR-06），每次哈希使用独立随机盐 |
| 存储字段 | `password_hash VARCHAR(72)`，禁止任何明文、可逆加密或 MD5/SHA1 |
| 强度校验 | 长度 ≥8，且同时包含大写字母、小写字母、数字（正则：`^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,64}$`） |
| 初始密码 | 管理员创建用户时生成 12 位随机密码，仅响应返回一次，不落库明文、不写日志 |
| 改密后动作 | `token_version + 1`、全部 Refresh Token 置 `revoked_at`、`password_changed_at = NOW()` |
| 接口响应 | 任何接口不得返回 `password_hash`；`User` schema 中无该字段 |

**（5）防攻击措施**

| 攻击 | 措施 |
| --- | --- |
| 账号枚举 | 登录失败统一提示；注册时用户名/邮箱唯一性提示改为"该学号已被注册或正在审核" |
| 暴力破解 | 账号维度 5 次/15 分钟锁定 + 登录接口 IP 维度令牌桶限流（10 次/分钟） |
| 令牌窃取 | Access Token 短有效期（2h）+ `tokenVersion` 即时失效 + Refresh Token 轮换与摘要存储 |
| 越权（IDOR） | 所有 `{id}` 路径均做归属校验；学生访问他人答卷返回 403 |
| SQL 注入 | 全部 `mysql2` 参数化查询；`ORDER BY` 字段使用白名单映射，不拼接用户输入（NFR-10） |
| XSS | 前端 React 默认转义；后端对题干/公告等富文本字段做 HTML 白名单过滤后再入库 |
| CSRF | 同域部署 + 令牌放在 `Authorization` 头（非 Cookie）；状态变更接口要求 `Content-Type: application/json` |
| 暴力遍历 | 答卷对外使用 `attemptNo`（UUID）而非自增 ID 暴露在分享/通知场景 |
| 传输 | 生产强制 HTTPS（Nginx HSTS），HTTP 301 跳转 |

**（6）登录失败锁定算法**

```js
// 15 分钟滑动窗口内的连续失败计数
async function handleLoginFailure(user) {
  const windowStart = dayjs().subtract(15, 'minute').toDate();
  const recentFailures = await auditService.countFailures(user.id, 'auth.login', windowStart);
  if (recentFailures + 1 >= 5) {
    await userModel.lockUntil(user.id, dayjs().add(15, 'minute').toDate(), recentFailures + 1);
    await auditService.write({ action: 'auth.lock', result: 'failure', userId: user.id });
  } else {
    await userModel.incrementFailures(user.id);
  }
}
```

> 说明：以 `sys_audit_log` 中的失败记录作为窗口数据源，避免额外缓存；`failed_attempts` 仅作冗余展示字段。锁定到期后首次请求自动解锁（`locked_until < NOW()` 时清零）。

| 场景 | 处理 | 响应码 |

**删除保护判定（REQ-QBM-03）**

```sql
-- 引用清单：未归档试卷 + 进行中/已发布的考试
SELECT p.id AS paperId, p.paper_name, p.status
  FROM pp_paper_question pq JOIN pp_paper p ON p.id = pq.paper_id
 WHERE pq.question_id = ? AND p.deleted_at IS NULL AND p.status <> 'archived'
UNION ALL
SELECT e.id, e.exam_name, e.status
  FROM pp_paper_question pq
  JOIN pp_paper p ON p.id = pq.paper_id
  JOIN ex_exam e  ON e.paper_id = p.id
 WHERE pq.question_id = ? AND e.deleted_at IS NULL
   AND e.status IN ('published','ongoing');
```

- 结果非空 → `409 QUESTION_REFERENCED`，`data` 返回引用清单；
- 结果为空 → `UPDATE qb_question SET deleted_at=NOW(), status='archived'`，并同步 `question_count`。

**批量导入**

1. 文件类型白名单：`.xlsx`、`.csv`；大小 ≤5MB；行数 ≤5000（超出直接拒绝，不截断）。
2. 逐行校验题型、选项、答案、分值、知识点；收集 `{rowNo, reason}`。
3. 采用"**部分成功**"策略：合法行入库，非法行返回明细（REQ-QBM-05 要求返回失败明细而非整批失败）；每 500 行一个事务批次提交，避免长事务。

### 3.4.3 随机组卷算法

```
输入：rules[{questionType, count, scorePerQuestion, difficultyDistribution}], bankIds[], knowledgePointIds[]
① 校验：Σ(count_i × scorePerQuestion_i) == totalScore，Σ difficultyDistribution == 1，否则 422
② 对每条规则构造候选池：
   SELECT id FROM qb_question
    WHERE bank_id IN (:bankIds)
      AND question_type = :type
      AND difficulty IN (:按分布展开的难度列表)
      AND knowledge_point_id IN (:kpIds)
      AND status = 'published' AND deleted_at IS NULL
      AND id NOT IN (:已选题目)
    ORDER BY RAND() LIMIT :count × 3      -- 取 3 倍候选，按难度配额二次筛选
③ 按难度配额从候选池抽取（不使用 ORDER BY RAND() 直接取最终结果，避免难度漂移）
④ 任一维度不足 → 汇总 shortages[{dimension, requiredCount, availableCount, shortageCount}]，返回 409，不落库
⑤ 全部满足 → 单事务写 pp_paper + pp_paper_question（快照取自 qb_question），返回试卷草稿
```

> `ORDER BY RAND()` 在 10 万题规模下为全表扫描；本期题库量按千级设计可接受，演进方案见 §2.3（预生成随机序列表）。候选池查询必须命中 `idx_question_bank_type`。

### 3.4.4 分值校验与状态约束

| 校验点 | 规则 | 失败响应 |
| --- | --- | --- |
| 题数与分值 | 至少 1 题；每题 `score > 0`；`Σscore == totalScore`（DECIMAL 比较，容差 0） | 422 `PAPER_SCORE_MISMATCH` + 差额 |
| 题目可用性 | 题目属于本人/被授权题库，且未软删除 | 403/422 |
| 题目去重 | 同一试卷不可重复引用同一题目 | 409 `PAPER_QUESTION_DUPLICATE` |
| 锁定状态 | `status='locked'` 时禁止改题目与分值，仅可改名称/说明 | 409 `PAPER_LOCKED` |
| 归档状态 | `status='archived'` 不可用于新建考试 | 409 `PAPER_ARCHIVED` |

**锁定时机**：`examService.createExam` 成功后，在同一事务内 `UPDATE pp_paper SET status='locked', used_count=used_count+1 WHERE id=? AND status IN ('draft','published')`；影响行数为 0 说明状态已变化，回滚并返回 409。

### 3.5.4 服务端权威计时（核心约束 2）

| 规则 | 实现 |
| --- | --- |
| 时间基准 | 全部使用 MySQL `NOW(3)`（UTC）与应用服务器时间，**不采信客户端时间** |
| 截止时间 | 开考时一次计算：`deadline_at = LEAST(started_at + duration_minutes, exam.end_time)`，写入答卷后不再变更 |
| 剩余时间 | `remainingSeconds = MAX(0, TIMESTAMPDIFF(SECOND, NOW(3), deadline_at))`，每次请求实时计算 |
| 校准频率 | 前端每 30s 调用 `remaining-time`；接口同时返回 `serverTime` 供前端校正本地偏移 |
| 交卷依据 | 仅服务端判定：`POST /submit` 时若 `NOW() > deadline_at + 5s 宽限`，仍按超时处理并标记 `submit_type='timeout'` |
| 超时兜底 | `timeoutSubmit.job` 每 30s 扫描 `status='ongoing' AND deadline_at < NOW()` 的答卷，调用同一 `submitAttempt`（`submitType='timeout'`） |
| 恢复语义 | 重连时返回同一 `deadline_at`，不重新计时；时间减少量与真实流逝一致 |

> **宽限期**：允许 5 秒网络往返与请求处理延迟，超过即判定超时；宽限期写入系统参数 `exam.submitGraceSeconds`，默认 5。

### 3.5.5 快照、脱敏与幂等（核心约束 2、3、4）

**（1）题目下发脱敏**

`attemptService.getAttemptQuestions` 采用**白名单投影**，而非"查全字段再删除"：

```js
// 只 SELECT 允许下发的列；snapshot 中的答案字段在应用层二次剥离
const rows = await attemptModel.listQuestionsForStudent(attemptId);
const questions = rows.map(r => ({
  attemptQuestionId: r.id,
  questionId: r.question_id,
  orderNo: r.order_no,
  questionType: r.question_type,
  stem: r.question_snapshot.stem,
  options: r.question_snapshot.options,      // 选项本身不含正确答案
  fullScore: r.full_score,
  studentAnswer: parseAnswer(r.student_answer),
  answerSavedAt: r.answer_saved_at,
})); // 明确不输出 correctAnswer / analysis / scoringPoints
```

**契约层的双重保障**：`api-contract.yaml` 中 `AttemptQuestion` schema **只定义** 8 个字段，不含答案字段；测试用例断言响应 JSON 中不存在 `correctAnswer|analysis|scoringPoints` 键（NFR-08）。

**（2）交卷幂等（条件更新 + 事务）**

```sql
START TRANSACTION;

-- ① 条件更新：只有 ongoing 才能交卷，影响行数即"是否为首次请求"
UPDATE ex_exam_attempt
   SET status = 'submitted', submitted_at = NOW(3), submit_type = ?
 WHERE id = ? AND status = 'ongoing';

-- 若 ROW_COUNT() = 0：说明已交卷/不存在 → ROLLBACK，直接读取当前结果返回（replayed=true）

-- ② 主观题生成阅卷任务（唯一索引防重复）
INSERT INTO mk_grading_task (exam_id, attempt_id, attempt_question_id, question_id, question_type, status)
SELECT a.exam_id, a.id, q.id, q.question_id, q.question_type, 'pending'
  FROM ex_attempt_question q JOIN ex_exam_attempt a ON a.id = q.attempt_id
 WHERE q.attempt_id = ? AND q.question_type IN ('short','fill')
   AND q.grade_status = 'pending';

-- ③ 更新任务状态
UPDATE ex_exam_task SET status = 'submitted'
 WHERE exam_id = ? AND student_id = ?;

COMMIT;
```

**并发保护**：条件更新本身对同一行加行锁，10 个并发交卷请求中仅 1 个命中 `status='ongoing'`，其余返回首次结果（需求 §8.4：并发交卷 10 次仅 1 条最终成绩）。

**（3）判分可重放**

```
autoGrade(attemptId):
  ① 读取答卷快照（ex_attempt_question.question_snapshot）——不查题库
  ② 事务内：UPDATE ... SET auto_score=0, final_score=0 WHERE attempt_id=? AND question_type IN ('single','multiple','judge','fill')
  ③ 逐题按题型判分器计算，写 auto_score / final_score / is_correct
  ④ 汇总 objective_score = Σ(auto_score)；subjective_score = Σ(COALESCE(manual_score,0))
  ⑤ total_score = objective_score + subjective_score；is_passed = total_score >= pass_score
  ⑥ 更新 grading_status（有主观题 → manual_pending，否则 auto_done）
```

重放一致性由"先清零再重算 + 只读快照"共同保证；重放不改变主观题人工得分（REQ-MRK-07）。

**（4）一致性校验（NFR-18）**

由 `statService.verifyConsistency(examId)` 与 `schema.sql` §8 的核对 SQL 双重保障：

- 答卷 `total_score == Σ(ex_attempt_question.final_score)`；
- 试卷 `total_score == Σ(pp_paper_question.score)`；
- 同一考生同一考试 `status='ongoing'` 记录数 ≤ 1（唯一索引保证）。

| REQ-MRK-01 客观题自动判分 | 交卷时同步判分（≤100ms/份），失败可重放 |

| REQ-MRK-05 成绩复核申诉 | 工单流转 + 改分留痕 |

### 3.6.2 阅卷任务状态机

```
pending ──第一评──> first_done ──需要双评──> second_pending ──第二评──> done
                        │                          │
                        │                          └─分差>20%──> arbitration ──仲裁──> done
                        └─单评模式──────────────────────────────────────────────> done

pending ──仲裁人直接裁定──> done
```

| 状态 | 含义 | 允许动作 |
| --- | --- | --- |
| `pending` | 待阅 | 第一评（`scoreGradingTask`） |
| `first_done` | 第一评完成（单评模式即完成） | 第二评 / 转完成 |
| `second_pending` | 等待第二评 | 第二评 |
| `arbitration` | 分差超阈值，待仲裁 | 仲裁（`arbitrateGradingTask`） |
| `done` | 完成 | 只读 |

### 3.6.3 人工评分规则

1. 得分必须 `0 ≤ score ≤ full_score`，否则 422（REQ-MRK-03）。
2. `scoringPointScores` 之和须等于 `score`（若提供），否则 422。
3. 保存后同一事务内：更新 `ex_attempt_question.manual_score / final_score / grade_status='manual'`，重算答卷 `subjective_score`、`total_score`、`is_passed`，写 `mk_grade_change_log`（`change_type='manual_grading'`）。
4. **双评约束**：第二评阅卷人不得与第一评相同（否则 409）。
5. **分差计算**：`score_gap = ABS(first_score - second_score)`；若 `score_gap > full_score × grading.arbitrationThresholdRatio`（默认 0.2）→ `status='arbitration'`。
6. **仲裁**：仲裁人须为管理员或被指定教研组长；写入 `arbitration_score`、`arbitrator_id`、`arbitration_reason`，`final_score = arbitration_score`，三方分数全部保留。

### 3.6.4 批量重判（REQ-MRK-07）

```
rejudgeQuestion(questionId, newCorrectAnswer, scope, operatorId):
  ① 校验调用者为 admin；题目存在且未被归档
  ② 更新 qb_question.correct_answer，current_version+1，写 qb_question_version(change_type='rejudge')
  ③ 定位受影响答卷：ex_attempt_question.question_id = ? AND attempt.status IN ('submitted','graded','reviewed')
  ④ 分批（每批 200 份）事务处理：
     - 仅对客观题型重算 auto_score / final_score / is_correct
     - 主观题 manual_score 与 final_score 保持不变
     - 重算 attempt 的 objective_score / total_score / is_passed
     - 写 mk_grade_change_log(change_type='rejudge', old, new, reason)
  ⑤ 汇总返回 {affectedAttempts, scoreChangedAttempts, failedAttempts, changeLogIds}
  ⑥ 写审计日志（action='question.rejudge'）
```

> 重判期间该题的新答卷判分使用新答案（已更新到 `qb_question`）；历史答卷使用各自快照，因此必须**显式重判**才变更（符合 C-15 的"快照不可自动变更"）。

### 3.6.5 复核申诉与成绩变更留痕

| 环节 | 规则 |
| --- | --- |
| 发起 | 仅本人、成绩已发布、`NOW() ≤ score_published_at + system.appealWindowDays`（默认 7 天） |
| 工单 | 写 `mk_score_appeal`（`appeal_no` 格式 `APL-YYYY-000001`），通知考试所有者 |
| 处理 | 教师/管理员：`accepted` 时必须提供 `newScore` 并写 `mk_grade_change_log(change_type='appeal', old, new, reason)`；`rejected/closed` 只写处理意见 |
| 留痕要求 | NFR-18：原值、新值、操作人、原因、时间缺一不可 |

### 3.7.3 物化策略（NFR-04）

```
触发点：交卷完成 / 阅卷完成 / 成绩发布 / 重判完成 / 管理员手动刷新
执行：statRefresh.job（去抖 5s，同一 examId 合并为一次）
写入：st_exam_stat（UPSERT on exam_id）
      st_question_stat（UPSERT on exam_id + question_id）
      st_knowledge_stat（UPSERT on exam_id + knowledge_point_id）
读取：GET /exams/{id}/statistics 先读物化表；calc_at 超过 300s 则同步重算并回写
```

**核心聚合 SQL（单场统计）**

```sql
SELECT
  (SELECT COUNT(*) FROM ex_exam_task WHERE exam_id = :examId) AS participant_count,
  COUNT(a.id)                                        AS submitted_count,
  ROUND(AVG(a.total_score), 2)                       AS avg_score,
  MAX(a.total_score)                                 AS max_score,
  MIN(a.total_score)                                 AS min_score,
  ROUND(STDDEV_POP(a.total_score), 2)                AS std_dev,
  SUM(a.total_score >= e.pass_score)                 AS pass_count
FROM ex_exam_attempt a
JOIN ex_exam e ON e.id = a.exam_id
WHERE a.exam_id = :examId AND a.status IN ('submitted','graded','reviewed')
GROUP BY a.exam_id;
```

**区分度计算（前后 27%）**

1. 按 `total_score DESC` 排序已交卷答卷，取前 `CEIL(N×27%)` 为高分组、后 `CEIL(N×27%)` 为低分组；
2. 对每道题分别计算两组平均得分率；
3. `discrimination = highRate − lowRate`，结果 ∈ [−1,1]，<0.2 视为区分度不足，写入 `abnormal_reason`。

**异常题判定**：正确率 <30% 或 >95% → `is_abnormal=1`，原因分别为"过难/可能存在答案错误"与"过易/区分度低"。

## 4 数据库设计

### 4.1 设计说明与分库策略

| 决策项 | 结论 | 依据 |
| --- | --- | --- |
| 数据库实例 | **单实例、单库 `oes`**，InnoDB，`utf8mb4` / `utf8mb4_0900_ai_ci` | C-03、C-08 |
| 分库分表 | **不做**。按 C-12 的设计量级（答卷 100 万、答题明细 500 万）单表可支撑 | C-12 |
| 逻辑分域 | 用**表名前缀**划分 7 个业务域（`sys_`/`kb_`/`qb_`/`pp_`/`ex_`/`mk_`/`st_`），为未来拆库预留边界 | 架构可演进 |
| 时间存储 | 统一 `DATETIME(3)`，**以 UTC 存储**，应用层按 `Asia/Shanghai` 展示 | C-10 |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`；对外敏感资源额外提供 UUID 业务号（`attempt_no`、`appeal_no`） | 防 ID 遍历 |
| 金额/分数 | `DECIMAL(5,2)`（单题分）、`DECIMAL(7,2)`（总分）、`DECIMAL(9,2)`（聚合分） | 避免浮点误差 |
| JSON 使用 | 仅用于结构多变的快照、选项、统计分布（`options`、`correct_answer`、`question_snapshot`、`score_distribution`） | 快照不可变、避免过度范式化 |
| 密码 | `VARCHAR(72)` 存 bcrypt 密文，任何表不存明文与盐（盐已内嵌于密文） | NFR-06 |

**容量估算**

| 表 | 年增量估算 | 100 万答卷对应规模 | 说明 |
| --- | --- | --- | --- |
| `ex_exam_attempt` | 约 20 万/年 | 100 万 | 单场 500 人 × 40 场/年 |
| `ex_attempt_question` | 约 100 万/年 | 500 万 | 每份答卷约 5 题 |
| `ex_anti_cheat_event` | 约 10 万/年 | — | 仅异常行为才写入 |
| `sys_audit_log` | 约 50 万/年 | — | 保留 180 天，超期归档 |
| `qb_question` | 约 5000/年 | — | 千级题库 |

**归档策略**：审计日志按 `created_at` 超 180 天转入 `sys_audit_log_archive`（同结构，无索引压缩）或导出 JSON 后清理；答卷与答题明细**不清理**（成绩需长期可查）。

### 4.2 命名规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 表名 | `模块前缀_业务名`，小写下划线，单数概念用复数语义但拼写保持简洁 | `qb_question`、`ex_exam_attempt` |

### 4.3 索引与约束策略

**索引设计原则**

1. 每个外键列必须有索引（InnoDB 外键要求），命名 `idx_*`。
2. 列表查询按「等值条件在前、范围/排序在后」建立复合索引：如 `idx_question_bank_type(bank_id, question_type, status)`。
3. 高频状态查询单独建索引：`idx_attempt_deadline`（超时扫描）、`idx_attempt_grading`（判分重放）、`idx_audit_created`（审计检索）。
4. 唯一索引承担业务约束：`uk_attempt_seq`、`uk_task_exam_student`、`uk_aq_attempt_question`、`uk_gt_attempt_question`、`uk_stat_exam`。
5. 避免在 `TEXT`/`JSON` 列上建普通索引；题干检索使用前缀匹配或后续引入全文索引。

**关键约束**

| 约束 | 实现 | 对应需求 |
| --- | --- | --- |
| 同一考生同一考试仅一条进行中答卷 | 生成列 `active_flag`（`status='ongoing'` 时为 1，否则 NULL）+ `uk_attempt_active(exam_id,student_id,active_flag)` | C-14、NFR-13 |
| 同一考生同一考试作答序号唯一 | `uk_attempt_seq(exam_id,student_id,attempt_seq)` | C-14 |
| 一份答卷每题唯一 | `uk_aq_attempt_question(attempt_id,question_id)` | NFR-18 |
| 一题一阅卷任务 | `uk_task_attempt_question(attempt_question_id)` | REQ-MRK-02 |
| 考试窗口合法 | `ck_exam_window CHECK (end_time > start_time)` | REQ-EXM-01 |
| 题型/难度合法 | `ck_question_type`、`ck_question_difficulty` | REQ-QBM-01 |
| 状态机合法 | `ck_attempt_status`、`ck_gt_status`、`ck_appeal_status` | 各模块 |
| 单场统计唯一 | `uk_stat_exam(exam_id)` | REQ-STA-02 |

### 4.4 软删除策略

| 数据类别 | 删除方式 | 字段 | 说明 |
| --- | --- | --- | --- |
| 用户 | 禁用（`status='disabled'`），不删除 | `status` | 保留历史考试与成绩 |
| 题库/题目 | 软删除 + 引用保护 | `deleted_at`、`status` | 被引用时 409（REQ-QBM-03） |
| 知识点 | 归档（`status='archived'`） | `status` | 被题目引用禁止删除 |
| 试卷 | 软删除 / 归档 | `deleted_at`、`status` | 被考试引用禁止删除 |
| 考试 | 取消 / 归档 | `status='cancelled'/'archived'` | 不物理删除 |
| 答卷/答题明细 | **永不删除** | — | 成绩与审计依据（C-16） |
| 阅卷任务/成绩变更 | **永不删除** | — | 追溯依据（NFR-18） |
| 公告 | 软删除 | `deleted_at` | — |
| 审计日志 | 不删除（超期归档） | `created_at` | NFR-09 |

**查询约定**：所有列表查询必须显式附加 `deleted_at IS NULL`（或 `status <> 'deleted'`）；软删除字段不参与唯一索引（用户名/编号不复用，故无需生成列变通）。

## 5 接口设计规范

### 5.1 RESTful 规范

| 项 | 规范 |
| --- | --- |
| 统一前缀 | `/api/v1`（NFR-16 向后兼容要求，版本号不可省略） |
| 资源命名 | 复数名词、小写、短横线；如 `/question-banks`、`/grading-tasks` |
| 层级 | 最多 2 级资源嵌套，更深语义用子资源接口（如 `/exams/{id}/statistics`） |
| 方法语义 | `GET` 查询（幂等）、`POST` 创建/动作、`PUT` 全量更新/幂等写、`PATCH` 局部更新、`DELETE` 软删除 |
| 状态码 | 200 成功、201 创建、202 异步受理、400 参数错误、401 未认证、403 越权、404 不存在、409 状态冲突、422 字段校验、423 锁定、429 限流、500 内部错误、503 降级 |
| 动作型端点 | 使用动词子路径表达不可映射为 CRUD 的动作，如 `/submit`、`/publish`、`/arbitrate`、`/rejudge` |
| 路径参数 | 资源 ID 用 `{camelCaseId}`，只允许数字或 UUID 格式 |
| 查询参数 | `page`、`pageSize`、`keyword`、`sortBy`、`order` 统一命名 |
| 幂等方法 | `PUT /attempts/{id}/answers`、`POST /attempts/{id}/submit` 必须幂等 |

### 5.2 统一响应体

```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

| 字段 | 类型 | 必有 | 说明 |
| --- | --- | --- | --- |
| `code` | integer | 是 | `0` 成功；非 0 为业务错误码（见 §5.4） |
| `message` | string | 是 | 成功为 `ok`；失败为**可直接展示的中文原因** |
| `data` | object/array/null | 否 | 业务数据；失败时通常为 `null`，409 时可携带冲突明细 |
| `errors` | array | 否 | 字段级校验明细 `[{field,message}]`（422 时返回） |

**约定**：HTTP 状态码与 `code` **同时**表达语义（前端可只依赖 HTTP 状态码处理通用分支，依赖 `code` 处理业务分支）；禁止"HTTP 200 + code 非 0"的伪成功（除兼容性极少数场景，本期不采用）。

### 5.3 分页规范

**请求**

```
GET /api/v1/questions?page=1&pageSize=20&keyword=TCP&questionType=fill
```

**响应**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [],
    "total": 137,
    "page": 1,
    "pageSize": 20
  }
}
```

| 规则 | 说明 |
| --- | --- |
| 默认值 | `page=1`、`pageSize=20`（REQ-QBM-04 明确默认 20） |
| 上限 | `pageSize ≤ 100`，超出截断为 100 并在日志记录 |
| 总数 | `total` 为符合筛选条件的总数（不受分页影响） |
| 排序 | 未指定时按业务默认（如 `created_at DESC`）；`ORDER BY` 字段白名单校验，禁止拼接用户输入 |
| 深分页 | 超过 1000 页时限制为前 1000 页（避免超大 OFFSET），提示进一步筛选 |
| 部分列表 | 普通数组（不涉及分页）直接放 `data`，如知识点树、角色、权限点 |

### 5.5 鉴权头与令牌

| 项 | 规范 |
| --- | --- |
| 请求头 | `Authorization: Bearer <accessToken>` |
| 公开接口 | `/auth/register`、`/auth/login`、`/auth/refresh`、`/health`（契约中 `security: []`） |
| 令牌算法 | HS256，密钥 `JWT_SECRET`（≥32 字节随机串，仅环境变量） |
| Access Token | 有效期 7200 秒；载荷 `{sub,username,roleCode,tokenVersion,jti,iat,exp}` |
| Refresh Token | 有效期 604800 秒；随机 32 字节，库中只存 SHA-256 摘要；每次刷新轮换 |
| 刷新接口 | `POST /auth/refresh`，请求体 `{refreshToken}`（**不放 URL**，避免日志泄漏） |
| 令牌失效 | 改密、角色变更、禁用账号时 `token_version + 1`，旧令牌下一次请求即失效 |
| 前端处理 | 401 且 `code=90203` 时自动刷新并重放一次；刷新失败清空本地状态跳转登录 |

## 6 非功能设计（安全、性能、部署）

### 6.1 安全设计

| 维度 | 措施 | 对应需求 |
| --- | --- | --- |
| 传输安全 | 生产强制 HTTPS（Nginx + HSTS），HTTP 301 跳转；禁用 TLS 1.0/1.1 | NFR-10 |
| 认证 | JWT HS256 + 令牌版本号 + 刷新令牌白名单与轮换 | REQ-UAM-01/03、NFR-07 |
| 授权 | RBAC 功能权限 + service 层数据权限双层校验；越权 403、未认证 401 | REQ-UAM-08、NFR-07 |
| 密码 | bcrypt(cost≥10) 加盐哈希；强度校验；改密强制重新登录 | REQ-UAM-07、NFR-06 |
| 答案保护 | 学生链路接口白名单投影，契约层面不定义答案字段；测试断言字段不存在 | REQ-EXM-04、NFR-08 |
| 注入防护 | 全参数化查询；`ORDER BY`/表名白名单；zod 入参校验 | NFR-10 |
| XSS | React 默认转义；富文本（题干/公告）HTML 白名单过滤；CSP 头 | NFR-10 |
| CSRF | 令牌置于 `Authorization` 头而非 Cookie；同域部署；写接口校验 `Content-Type` | NFR-10 |
| 暴力破解 | 账号锁定 + 登录/注册 IP 限流 | REQ-UAM-02 |
| 敏感信息 | 日志与响应禁用密码/令牌/答案；`requestSummary` 脱敏 | NFR-06、NFR-09 |
| 审计 | 敏感操作自动落库，仅 INSERT，应用账号无 UPDATE/DELETE 权限 | REQ-SYS-02、NFR-09 |
| 越权遍历 | 答卷/申诉对外使用 UUID 业务号；所有 `{id}` 做归属校验 | 权限矩阵 §3.3 |
| 依赖安全 | `npm audit` 纳入 CI；锁定版本并提交 lock 文件 | 需求 §7.5 |

### 6.2 性能设计

| NFR | 指标 | 设计措施 | 验证 |
| --- | --- | --- | --- |
| NFR-01 | 200 并发提交，P95 ≤2s、P99 ≤4s、错误率 ≤0.1% | 连接池（`connectionLimit=20`）；答案暂存单条 UPDATE；批量暂存合并为一次 `CASE WHEN` 或逐条事务批次；不写大字段日志 | k6 压测 `PUT /answers` |
| NFR-02 | 局域网 LCP ≤2.5s；路由切换 1s 内出现骨架 | Vite 按路由 `import()` 分包；ECharts 懒加载；首屏仅加载登录/工作台壳；骨架屏 | Lighthouse |
| NFR-03 | 1000 份答卷 10s 内完成客观判分；单份 ≤100ms | 判分纯内存计算 + 批量事务；每 200 份提交一次；无外部 IO | 批量交卷压测 |
| NFR-04 | 10 万答卷统计 ≤3s | `st_*` 物化 + `uk_stat_exam` UPSERT；统计只读汇总表；必要时异步刷新 | 预置数据计时 + 慢查询日志 |
| NFR-05 | 列表接口 P95 ≤500ms | 复合索引；前缀匹配；`COUNT(*)` 与列表分离；禁止 `SELECT *` | 接口压测 + EXPLAIN |
| 容量 | 单场 500 人 | 连接池 20 + 查询轻量；开考写入为单事务（1 答卷 + N 明细）；超时任务分批 100 条 | 压测 |

**关键查询优化**

| 场景 | 策略 |
| --- | --- |
| 开考复制快照 | `INSERT ... SELECT FROM pp_paper_question` 单条 SQL 完成批量插入，避免 N 次往返 |
| 答案暂存 | 按 `(attempt_id, question_id)` 唯一索引定位单行 UPDATE |
| 超时扫描 | `idx_attempt_deadline(deadline_at)` + `INDEX` 条件 `status='ongoing'`，每批 100 条 |
| 成绩列表 | 按 `exam_id + status` 过滤后排序，`idx_attempt_exam_status` |
| 防止 N+1 | service 层统一"一次查询 + 内存组装"，如试卷详情一次查明细再一次查题目名 |

### 6.3 可靠性设计

| NFR | 要求 | 措施 |
| --- | --- | --- |
| NFR-11 | 答案不丢失，恢复成功率 100% | 30s 自动暂存 + 每次切题暂存；答案落库后再返回成功；断线恢复读同一答卷；服务重启后数据在库，不依赖内存 |
| NFR-12 | 考试窗口可用性 ≥99.9% | PM2 崩溃自动拉起；`/health` 供监控；MySQL 每日备份；故障时只读降级（可选） |
| NFR-13 | 交卷与判分幂等 | 条件 UPDATE + 唯一索引 + 判分先清零再重算 + 定时重放；并发交卷仅 1 条最终成绩 |
| NFR-18 | 成绩一致性 | `total_score = Σfinal_score` 由 service 统一重算；一致性核对 SQL；变更留痕表 |
| 数据备份 | 每日逻辑备份 | `mysqldump --single-transaction`，保留 7 份，月度恢复演练 |

**故障恢复顺序**：MySQL 恢复 → 启动 Node（自动执行未完成的备份/统计补跑）→ 定时任务自动接管超时交卷与判分重放 → 校验一致性。
